# Supabase

Multi-tenant database for Mezo. Central invariant: **every
restaurant-owned row carries `restaurant_id`, authorization is enforced by
Postgres Row Level Security, and the service-role key is never available to the
browser.**

## Contents

- `config.toml` — CLI configuration generated by `npx supabase init`.
- `migrations/` — ordered, transactional SQL migrations. Never edit a migration
  that has been applied anywhere; add a new one instead.
- `seed.sql` — development subscription plans only. No accounts, passwords or
  credentials.

## Applying migrations locally

`npx supabase start` requires Docker Desktop. Once installed:

```bash
npm run db:start    # boot the local stack
npm run db:reset    # drop, recreate, re-apply every migration and the seed
npm run db:push     # push migrations to the linked remote project
npm run db:types    # regenerate src/types/database.ts from the local stack
```

`supabase db push --dry-run` shows exactly what would be applied against a
linked project; never use `--include-seed` in production.

## Verifying without Docker

Docker Desktop is not installed on the development machine used for Phase 2.
Instead, the test suite applies every migration to a real, in-memory PostgreSQL
17 instance (PGlite) and exercises the policies as `SET ROLE`-selected
identities:

```bash
npm run test:db
```

`tests/db/harness.ts` creates a test-only `auth` schema shim
(`auth.users`, `auth.uid()`), creates the `anon`, `authenticated` and
`service_role` roles, and applies the migrations in filename order. The shim
is never committed as a migration. It mirrors Supabase closely enough to test
RLS, privileges and SECURITY DEFINER functions.

RLS is verified by switching identity per transaction, exactly like Supabase's
authenticated clients, never by reading the policy definitions alone.

### Hosted staging project

Phase 2 was also verified against the dedicated **mezo-staging** Supabase
project (`sskooncjmymzoxlhkulh`, PostgreSQL 17.11, `eu-central-1`).

- Migrations were applied with `supabase db push --remote` and inspected with
  `supabase migration list --remote` (**18 applied, remote history matches
  local**; includes `20261112110000_enforce_non_anonymous_on_apply.sql`,
  `20261112120000_staff_invitations.sql`,
  `20261112130000_invitation_fixes.sql`,
  `20261112140000_restrict_slug_and_anonymous_accept.sql`,
  `20261112150000_subscription_management.sql`, and
  `20261112160000_menu_management.sql`; the storage buckets `restaurant-logos`
  and `menu-images` were created there).
- Because the direct database host (`db.<ref>.supabase.co`) is not reachable
  from this network, the session pooler is used instead:
  `aws-1-eu-central-1.pooler.supabase.com:5432`.
  `.env.local` (git-ignored, never committed) carries `MEZO_STAGING_PROJECT_REF`,
  `NEXT_PUBLIC_SUPABASE_URL`, keys, and `SUPABASE_DB_PASSWORD`.
- Run the same 93 checks against staging:

  ```bash
  npm run test:db:staging
  ```

  This reuses the shared suite through `tests/db/staging.test.ts` with a
  transaction-scoped `SET LOCAL ROLE` probe (the pooled session does not
  preserve `SET ROLE` across statements). 93 = 47 Phase 3 checks + 46 Phase 4/5
  checks (profile update, tenant isolation, invitation lifecycle, deactivation,
  multi-membership, slug immutability, subscription lifecycle and limits).

- The staging run is **not** idempotent at the fixture level: the suite
  deletes only the fixture slugs and `example.test` users before recreating
  them, so re-running is safe and leaves the fixture data in place after the
  run for inspection.

`pglite` remains the default for CI-like local runs; staging is the final gate.

## Roles

`restaurant_role` enum values are exactly `restaurant_admin`, `waiter` and
`kitchen`. `platform_admin` lives exclusively in `public.platform_admins`.
Do not add new roles back without updating `src/lib/security/roles.ts`,
`src/lib/validation/roles.ts`, this enum and every policy that references it.

The registering user of a restaurant application becomes its first
`restaurant_admin` when a platform administrator approves the application via
`public.review_restaurant_application()`.

## Public surface

There is no public read access to any base table except:

- `subscription_plans` (active plans, pricing catalogue),
- `menu_categories` / `menu_items` (active rows in publicly available
  restaurants),
- `public_restaurants` (a view with safe restaurant fields only, `security_invoker = false`),

and even then only rows belonging to restaurants that are both `approved` and
`active`. QR table tokens and everything about occupancy, guests, orders,
payments, subscriptions and audit logs are staff-only, and audit/webhook
tables are platform-admin-only.

## Phase 4 objects: staff invitations, logos, and slug immutability

Migrations 14–16 add `restaurant_staff_invitations` (roles `waiter`/`kitchen`
only, single-use, ~244-bit tokens stored as a hash, 7-day TTL) plus the
`restaurant-logos` storage bucket (2 MB, PNG/JPEG/WebP/AVIF, public read,
restaurant-admin write on the folder matching the restaurant id), cleanup
fixes (column-scoped grant on the invitation table, unambiguous RPC bodies,
portable token hashing), and slug immutability (`UPDATE (slug)` revoked from
`authenticated`; `protect_restaurant_review_fields()` extended to guard slug).
Invitations are issued and consumed through the `SECURITY DEFINER` RPCs
`invite_restaurant_staff`, `accept_restaurant_invitation`,
`revoke_restaurant_invitation` and `deactivate_restaurant_member`; all four
authorize off the caller's JWT and require the caller to be an active
`restaurant_admin` of the restaurant (anonymous JWT callers are rejected).
**No email is sent by the database** — delivery is out-of-band (the admin
shares the one-time link manually). The token hash is `md5(token)`: unsalted
by design, safe for a ~244-bit random input, and portable across vanilla
PostgreSQL and PGlite (which lacks pgcrypto). service_role keeps full access;
clients never see `token_hash`. The `/accept-invite` page is served with
`Referrer-Policy: no-referrer`, `no-store` cache headers and
`noindex, nofollow` robots metadata, and strips the token from the address
bar / browser history on mount.

The invitation acceptance path is `…/accept-invite?token=…` in the app; the
token is verified against the calling user's email, is single-use, and is the
only bearer secret involved. Anonymous sessions are rejected, and the page
removes the token from the URL on mount.

## Phase 3+ endpoints for the guest QR flow

- Anonymous sign-ins are **enabled on staging** (as of 2026-11-12). The guest
  QR flow (Phase 4+ when that phase is approved) will consume this path:
  `signInAnonymously()` is available on the staging project and lives at
  `src/lib/auth/anonymous.ts`. Anonymous sessions are real
  `authenticated`-audience users with `is_anonymous: true`; they cannot reach
  any staff route and have zero restaurant memberships.
- `config.toml` targets local dev at `http://127.0.0.1:3000`; staging was
  pushed and verified on 2026-11-12.

## Type generation

Regenerate after applying migrations:

```bash
npm run db:types
```

or, when the pooler is not reachable from the current network or for a linked
remote project:

```bash
npx supabase gen types typescript --project-id <ref> > src/types/database.ts
```

(`--project-id` is deprecated in CLI v4 and will be removed; prefer
`--remote` when the direct DB connection is reachable.)

`src/types/database.ts` is generated from the schema and should be
regenerated on every schema change — never hand-maintained. See
`PROJECT_STATUS.md` for the full inventory.
